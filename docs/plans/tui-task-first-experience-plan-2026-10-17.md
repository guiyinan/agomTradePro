## 1. 要解决的问题

用户不应为了研究一个标的或检查组合，先学习系统模块、内部八步流程、提示词编排和服务接入。产品应让用户带着问题进入，在同一任务中拿到可理解、可核查的结果，并知道结果的限制和下一步。

目标是降低系统操作成本，同时保留专业研究深度。投资知识、证据判断和用户决策仍有必要；系统应承担能力发现、数据准备、上下文传递和结果组织的工作。

本次“太重”首先指认知和操作负担。资源占用、响应速度、请求数量另行测量，不能从页面简化推断性能已提升。

## 2. 建议的产品结构

采用同一 `/tui/` 内的两种工作模式，加一个独立诊断入口：**任务模式（默认）／专业模式／调试工具（受权限控制）**。

| 区域 | 面向谁 | 用户看到什么 | 与现有能力的关系 |
| --- | --- | --- | --- |
| 任务模式 | 有基本投资知识、不了解系统结构的用户；目标人群待讨论 | 今日关注、研究标的、检查组合；当前任务、结果、证据和下一步 | 通过策划后的任务编排调用已有能力 |
| 专业模式 | 需要深挖证据、调整研究参数、比较方法的用户 | 现有研究工作区、八步流程、详细图表、参数及有权执行的操作 | 保留现有主任务闭环，并逐项整理入口 |
| 调试工具 | 已获授权的维护和诊断人员 | 脱敏调用追踪、失败阶段、技术状态、受控诊断操作 | 从现有诊断用途中明确分离，不整包照搬全部 action |

模式只影响组织方式和展示深度，不能授予新权限。普通用户可以使用其有权访问的专业研究能力；管理员也默认进入任务模式，通过独立入口处理治理工作。

“专业”不等于“调试”。账户管理、个人服务接入、正常写入操作不能因复杂就统一塞进调试工具。账户与安全设置保留稳定的个人入口；数据、AI、MCP、QMT 等全局治理保留管理员入口。

### 模式切换与兼容约束

1. 顶层可发现“任务模式／专业模式”，记住用户明确选择的偏好；不按操作次数自动切换。
2. 任务结果提供“深入研究”，携带标的、账户范围、数据基准日和已授权查询条件进入对应专业工作区；可以返回原任务。
3. 保留既有 screen/action deep link、地址定位、键盘路径和浏览器历史语义。旧链接打开其对应专业任务，不静默落到新首页，也不重写全局模式偏好。
4. 切换不提交表单、不重新触发 AI、不重复写入。未提交内容先提示保存或离开；敏感信息不写入 URL、模式偏好或持久化缓存。
5. 切换与任务恢复后重新检查权限和事实状态。确认授权、短期 continuation、已过期数据不能跨模式自动续用。

## 3. 默认入口与三条任务

默认首页以三个清晰任务入口和“继续上次任务”为主。一次只呈现一个主要推进动作；证据展开、返回和取消保持可达。无需走新手问卷或配置全部服务后才进入研究。

| 入口 | 最小输入 | 应交付的结果 | 需要额外条件时 |
| --- | --- | --- | --- |
| 今日关注 | 可直接查看明确标注范围的市场关注；个性化需要自选或组合 | 与当前范围有关的变化、风险及待办；没有待办也要明确说明 | 尚无自选时展示市场范围，不能冒充个人影响分析 |
| 研究标的 | 输入名称或代码，并在有歧义时选择明确资产与市场 | 研究摘要、主要依据、反面因素、证伪条件、源观测时间、可用性与下一步 | 缺数据或能力时明确不完整范围；不能伪造完整报告 |
| 检查组合 | 选择已有组合；也可进入有边界的导入或示例体验 | 风险问题、约束检查、证据和可继续研究的事项 | 无持仓时解释导入需要的最少字段；示例独立标识 |

建议先完成“研究标的”。这条路径无需先导入账户，适合验证首次价值。首批具体支持哪些资产和输出，阶段 A 按真实 owner 能力确定；不以通用名称承诺全资产完整支持。

### 首条路径示例（拟议行为）

```text
任务首页 → 研究标的 → 输入名称/代码 → 必要时确认标的
        → 自动准备已有材料与可用性检查
        → 研究摘要 + 依据 + 风险/证伪 + 数据时间/限制
        → 查看证据 / 深入专业工作区 / 有权保存或加入自选
```

系统自动完成已批准的被动查询和上下文准备。AI 生成、付费能力、写入、审批、交易继续要求适当的明确用户动作及原权限/确认合同；“开始研究”的按钮必须说明是否包含 AI 与费用，不能因打开页面或模式切换而调用模型。

AI 不可用时仍可呈现真实结构化事实和缺口，不把确定性摘要伪装成已完成的 AI 研究。不增加需要用户学习的专用提示词；对话和固定按钮进入同一任务及结果合同。

## 4. 任务内的信息层次与异常恢复

### 首层必须可见

- 本次研究对象、组合/市场范围、数据基准日。
- 关键发现、主要依据及反面证据；仅在证据支持范围内形成结论。
- 影响理解的源观测时间、时效、可靠性、缺失项与决策/执行限制。
- 当前处理状态、用户下一步，以及取消或重试入口。

方法细节、完整图表、参数和原始证据可逐层展开。`must_not_use_for_decision`、`must_not_execute`、稳定阻断原因以及证伪阈值不能被折叠成看不见的高级选项。

### 状态按业务结果解释

| 场景 | 面向用户的反馈 | 恢复方式 |
| --- | --- | --- |
| 首次使用/无持仓 | 说明当前能做什么、还缺什么 | 研究标的、导入持仓或使用明确标识的示例 |
| 数据缺失、过期或不可靠 | 指出受影响的发现与使用限制 | 可阅读已有事实；需要管理员处理的任务明确归属，不让用户维护数据源 |
| 部分能力失败 | 保留已成功的材料，说明缺失部分 | 只重试失败的安全步骤；不把 partial 标成完整成功 |
| 长任务或网络异常 | 展示本次任务状态；不能确认时标明结果待核实 | 查询同一运行；遵守已有幂等重试合同，不另起重复 AI/写入 |
| 服务未配置或额度不足 | 说明哪些能力受限、谁可处理 | 保留可用路径；按需配置个人服务或联系管理员 |
| 取消/离开 | 区分停止等待与后台任务实际取消 | 能力不支持后台取消时如实说明；不承诺撤销已生效写入 |

示例数据应显著标注“示例”，与真实账户和事实数据隔离；示例成功不代表个人组合可用或决策门禁通过。导入持仓要有字段校验、预览确认和失败反馈，不静默替换现有组合。

## 5. 现有能力如何安置

| 当前能力 | 建议归属 | 任务模式中的使用方式 |
| --- | --- | --- |
| 今日总览 | 改为任务模式的轻首页；详细摘要留在专业模式 | 呈现有关的关注项与继续任务，避免多个摘要面板争夺首屏 |
| 环境与脉搏、政策与热点、Beta/Alpha、资产研究 | 专业模式的研究工作区 | 作为任务依据按需展开，用户无需逐屏收集 |
| 每日决策流、策略与风控、事件与复盘 | 专业模式保留完整闭环 | 根据本次任务关联约束与记录，不强制新用户每天完成八步 |
| 账户与持仓 | 任务模式提供组合选择与检查；专业模式保留详细管理 | 创建/导入、变更、模拟与实盘操作逐项策划并保持清晰风险边界 |
| AI 任务助手 | 共用任务入口与任务结果 | 自然语言是可选输入方式，固定按钮可以独立完成任务 |
| 提示词模板与执行链、命令行任务台 | 按既有权限置于专业工具 | 不作为首次研究的必修步骤 |
| 我的 AI 服务商、我的 MCP、个人资料与安全 | 个人设置/接入入口 | 需要时引导，不要求首次全配齐 |
| 数据/AI/MCP/QMT 全局治理 | 管理员工作区 | 用户仅看到相关影响、处理归属和可行下一步 |
| 路由目录、原始响应、技术调用与调试动作 | 独立调试工具 | 保持后端授权、脱敏及审计，不通过切换模式获取权限 |

阶段 A 建立全量能力去向表，以当前运行时可见 screen/action、角色及主任务为准，覆盖 published 与 runtime 注入项。每项明确“任务复用／专业保留／管理员治理／诊断／待审查去重”，防止简单隐藏导致任务失联。仍有用户价值的能力不为减少菜单数而删除。

## 6. 技术实施边界（供讨论，不在本次改代码）

1. **一个运行时与一套业务真源。** 两种模式共享 owner Application、权限、结果证据、审计和写入合同；不复制一套简化业务规则。
2. **IA 仍是导航真源。** 模式归属、默认入口和专业深链从现有 IA 注册表演进。需要新元数据时成套更新 schema、validator、compiler、runtime 与测试；本文字段设想不作为可直接使用的 schema。
3. **业务编排归 owner。** 跨业务能力通过公开 Application、Protocol/Facade 组装；terminal 只提供任务呈现、交互与调度合同，不承担金融规则、ORM 查询或新的准入判断。
4. **通用渲染与产品策划分开。** 通用 runtime 支持可复用的层级、步骤和状态；AgomTradePro 的任务名称、标的/组合语义及映射放在宿主与业务侧，不硬编码进入通用引擎。
5. **复用当前任务与恢复机制。** 先核对现有 task/run、分页、结果 continuation 和重试能力，再决定最小扩展；不为本计划先建一个新的万能工作流引擎。
6. **模式不是安全边界。** 导航、catalog、直接加载、action-run 与 owner 授权都须一致；调试工具输出也必须脱敏，不能展示凭据或绕开对象归属。
7. **按需加载。** 进入任务时只加载当前必要信息，证据展开后读取辅助内容；记录真实首个有用结果时间、请求数量与失败情况，不用 mock 计时证明线上提速。
8. **先用已有事实。** 后续若新建或改变 current/summary 合同，遵守[数据新鲜度规范](../development/data-freshness-contract-guard.md)并登记 `current_data_contracts.json`；不新增“排序最新即安全可用”的推断。
9. **延续迁移纪律。** 新主任务仍进入 `/tui/`；改变 Classic 目标映射时同步[迁移计划](web-to-tui-migration-plan-2026-07-25.md)及矩阵。新 UI 不代表 M5 放行，也不继承旧候选生产验收。

## 7. 分阶段推进与退出条件

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| A：讨论与基线 | 确定首批用户、模式边界、第一任务；盘点现有能力与真实权限；记录现状操作路径 | 产品决策明确；每个现有主任务都有去向；首任务支持范围和能力缺口可复核 |
| B：任务原型 | 默认首页、单标的研究结果、证据展开、专业切换、空态/阻断/失败原型 | 目标用户无需讲解能理解入口、结果限制和下一步；原型使用示例须标识，不算业务 UAT |
| C：首条纵向实现 | 同一运行时内交付“研究标的”完整路径和专业回程；补必要 owner 接口 | 真实登录角色完成输入到结果及恢复；对话/按钮一致；权限、时间与禁止标记、旧深链均通过回归 |
| D：扩展两条任务 | 今日关注、组合检查；按需接入及有边界的示例/导入 | 三条任务覆盖首批用户需要；无持仓/服务不可用仍有明确下一步；模拟与实盘不混淆 |
| E：验证与推广 | 新用户验证、对照旧路径、性能观测、迁移说明与回滚演练 | 达到约定指标后才扩大默认入口；生产验收绑定新候选，按既有发布流程推广 |

用户已授权按本文推荐方向实施。阶段 B 的具体合同与回归设计先由主代理和 Luna Max 复核，再进入对应代码切片；先登记唯一 closure unit、依赖和退出门，并协调 repository 集成窗口。不做整套主题重绘、新前端框架或交易能力扩张。

### 7.1 与正在运行的 A 股 Goal 并行的边界

2026-10-17 用户要求核对与 [梳理数据字典能力与缺口](codex://threads/01a14268-4d88-75e2-812a-fdbdd60b1b24) 的并行可行性。本次读取该 chat 的近期进展、[A 股主计划](a-share-usability-implementation-plan-2026-10-16.md)、当前 Git 变更及机器注册表；以下是该次核对的分工建议，不是启动代码并行的授权，也不替代实时执行焦点。

**结论：现在可并行推进产品讨论、能力盘点和独立原型；生产代码按冻结合同分批交接，不要求等待整个 A 股 Goal 完成。**

该 Goal 的近期工作涉及自动交易结果、SDK/MCP 账户范围和费用处理；其完整范围还包括数据能力、组合约束、调仓 TUI、复盘和用户验收。近期已触及 TUI 测试、IA、runtime 注入及生成 manifest，不能假定“一个改后端、一个改前端”就天然无冲突。

| 本计划工作 | 与 A 股主线关系 | 并行安排 |
| --- | --- | --- |
| 用户画像、三条任务、专业/调试边界、文案与验收脚本 | 不改变业务行为 | 可立即作为讨论和治理工作推进 |
| 现有能力去向、只读接口与角色盘点 | 有语义依赖，尚无写入冲突 | 可只读核对；记录缺口，不能用原型假设补造能力 |
| 任务首页、结果层次、模式切换的独立原型 | 可用明确标注的示例说明交互 | 可先做隔离原型；不修改生产 IA/runtime、不作为真实业务验收 |
| 默认入口、专业模式切换、共享导航及状态恢复 | 与现有 TUI 外壳、deep link、确认和重试共用代码 | 冻结共享合同后按单一集成窗口接入，不能同时改同一生产外壳 |
| 标的研究接入 | 依赖现有研究 owner；数据可用性与 ASH-04 重叠 | 已验证部分可单独切片；缺失/阻断状态照实呈现。涉及新能力语义时先与 ASH-04 对齐 |
| 组合检查、调仓、成交导入与复盘 | 与 ASH-03/04/07/08/10 直接重叠 | A 股主线负责金额、股份、规则、约束、计划与回执；本计划负责默认任务入口和分层呈现，共用同一业务工作区，不另造调仓实现 |
| 真实浏览器验收与发布 | 与 ASH-11 及现有候选验收共用事实和版本 | 产品可用性与交易正确性分别断言，绑定同一集成候选后联合验收；不将两份原型或不同 SHA 的测试拼成通过 |

#### 代码施工前的交接条件

1. 先确定首个小切片及其源提交、文件责任人、允许修改的路径和结果合同。优先选择“任务入口 + 单标的研究”，组合/执行路径继续由 A 股主线推进。
2. 共享修改点至少包括 IA 注册表、TUI schema、terminal 的元数据/结果投影、前端导航/动作/工作状态、`test_tui_workbench.py`、runtime manifest、计划索引及机器登记。实际清单在领取切片前重查；不同文件也须核对是否共享字段和状态语义。
3. 当前机器执行策略只允许单一 repository 集成焦点。新增生产代码切片须先在注册表登记并明确获准的焦点/子批次关系；本次用户询问并行可行性不改变该策略。独立目录或 checkout 只能减少文件冲突，不能自动解除执行锁。

## 9. 风险与回滚点

- **两种模式重复维护：** 共享业务合同和证据，仅策划呈现深度；首条纵向路径先证明复用成立，再扩展。
- **只是隐藏按钮：** 验收完整研究结果和异常恢复；只缩短菜单、仍需用户跨屏拼数据不能验收。
- **过度依赖 AI：** 固定任务入口独立可用，明确 AI 与费用；模型不能修改事实时间、隐藏阻断或自行发起交易。
- **专业用户效率下降：** 旧工作区和 deep link 保留；上线前用代表性连续任务对照验证。
- **任务持久化引入敏感数据：** 偏好、查询上下文、业务结果和授权凭证分别核对保存范围；不把敏感结果塞进浏览器持久化状态。
- **变更污染现有生产证据：** 若修改发布图谱、schema/runtime 或矩阵，以新候选重新核对受影响证据，不能沿用旧候选 UAT 宣称通过。

回滚以匹配的 IA、schema、服务端读取/编译、前端 bundle 与 manifest 为单位。默认入口可回到已验证的专业工作区；新任务入口须先撤下或禁用，再回退不理解新合同的客户端。保留已产生的业务记录、审计和运行身份；UI 回滚不撤销已生效写入，也不自动恢复旧权限或旧数据有效性。
