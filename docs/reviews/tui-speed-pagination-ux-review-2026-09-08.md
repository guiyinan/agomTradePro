# TUI UI/UX 专项评审：响应速度与分页

日期：2026-09-08；代码基准：`285733cb6`。

本报告按用户补充意见，将评审重点调整为“用起来太慢”和“分页不合理”。此前的操作逻辑报告作为补充材料，实施优先级以本专项建议为先。

## 1. 结论

用户感受到的慢，需要拆开看：**数据真正返回得慢、交互反复清空重建、寻找和翻阅信息成本高**。当前源码已能确认后两类机制；第一类尚无真实会话的请求瀑布和服务端耗时数据，不能认定是数据库、网络或某个服务导致。

分页不只是按钮数量的问题。当前存在三套不同体验：普通结果表分页、概览表截取少量记录、可筛选概览表展示全部返回行。它们对搜索范围、总数、查看更多和返回位置的表达不统一，值得优先整改。

建议先完成：**翻页不清屏、统一表格模式、明确全量搜索与当前页筛选、返回保留位置**。随后基于真实测量减少慢请求和非必要加载。暂不建议通过换主题、全面更换前端框架或增加更多面板解决这些问题。

## 2. “慢”的 UI/UX 问题

| 问题 | 当前证据 | 用户感受 | 建议 |
|---|---|---|---|
| 切屏先清空主区域，再等新屏返回 | `loadScreen` 在请求前写入加载占位 | 每次切换都像重新启动，原来的信息立即消失 | 首次加载用稳定骨架；后续切屏保留稳定外壳。若暂留旧内容，明确标记旧页面并禁止旧对象写操作 |
| 服务端翻页走完整动作执行链 | `pageDelta → runAction → renderActionLoadingState → renderViewModel` | 只是翻一页，也要经历整块结果加载与重绘 | 表头、筛选、分页条保持不动；只更新表体，显示局部加载，失败保留原页并就地重试 |
| 返回同一屏仍重新加载、重新初始化筛选 | `loadScreen`、`renderScreen`、`renderDashboardHome` | 看详情后回来又等一次，还得重新找原位置 | 保留用户、工作区、查询条件对应的页面状态；展示最近结果时标记更新时间并后台核验，写入后使相关缓存失效 |
| P1 面板很快就与 P0 竞争加载 | P0 发起后用 `requestIdleCallback`，最长等待参数 250ms，启动其余可见面板 | 主内容还没回来，辅助信息也开始请求 | 主任务关键面板优先；辅助面板按进入视口或展开加载，控制并发，并测量真实后端竞争情况 |
| 每次动作完成还会触发导航徽标刷新 | `runAction` 完成后调用 `refreshGovernanceBadges`；存在 host hook 与首页聚合复用 | 翻页等纯读取也进入附加刷新逻辑 | 对只读翻页避免无关徽标更新；按角色、失效事件和短时合并策略更新。实际额外网络数需测量，不能按调用次数直接推断 |
| 当前首屏计时早于关键数据完成 | `p0-ready` 在 `renderScreen` 后打点，面板请求仍异步执行 | 指标可能显示“已经快了”，用户还在等内容 | 分别记录外壳可见、首个有效主内容、关键面板全部完成、可交互和后台加载完成 |

已有优化必须保留：合并 bootstrap、P0 先发起、P2 展开加载、旧请求取消、首页部分聚合复用，以及后端 metadata runtime 缓存。这里不是建议“从零加缓存”，也未证明这些缓存线上命中正常。

缓存中的决策数据仍应发布原始观测时间、可靠性、时效和禁止用于决策状态。不能为了视觉上快而把旧数据显示成最新可用结果。

证据：[切屏与动作加载](../../frontend/tui-workbench/src/30-actions.js#L710)、[面板调度](../../frontend/tui-workbench/src/20-dashboard.js#L71)、[徽标刷新](../../frontend/tui-workbench/src/00-runtime.js#L944)、[首屏打点](../../frontend/tui-workbench/src/50-shell.js#L994)、[后端 metadata 缓存](../../apps/terminal/infrastructure/tui_metadata_repository.py#L70)。

## 3. 分页为什么不合理

### P1：同一系统有三种表格展示规则

| 表格位置 | 当前机制 | 体验缺口 |
|---|---|---|
| 普通结果表 | 有服务端 pager 时按服务端分页；没有 pager 时，客户端默认 100 行一页 | 用户看不出搜索的是当前页还是全部已加载结果，也不能从通用分页条选择每页数量 |
| 普通概览表 | 通用渲染器取 `max_rows`，默认前 8 行 | 该渲染器不消费 pager，也不直接显示分页或剩余条数；仅看到几条记录，容易误认为已经看完 |
| 带筛选的概览表 | 展示全部 `viewModel.rows`，忽略 `max_rows` 截取 | 增大返回数量后，表格变长，增加滚动和 DOM 渲染量；“实际展示 N 条”不是整个数据集总数 |

个别业务扩展 renderer 可能另有实现，因此上述结论限定于通用渲染路径。概览卡片可能提供打开动作或跳转，不能据此认定剩余数据一定无法访问；问题是列表本身没有统一、明确的“剩余数据在哪里”。

**建议只保留两种面向用户的模式：**

- **摘要卡片：**展示少量最重要记录，明确“显示前 8 条”，提供可点击的“查看完整列表”。只有后端提供可靠总数时才显示“共 N 条”。
- **完整工作列表：**使用统一筛选、排序和分页区。操作密集列表可先试 20 行，扫描型列表可先试 50 行，提供 20/50/100 选项；这些是待验证的产品默认值，不是未经测量的性能结论。

证据：[普通表格分页](../../frontend/tui-workbench/src/40-views.js#L114)、[概览表通用渲染](../../frontend/tui-workbench/src/20-dashboard.js#L675)、[客户端默认页大小](../../frontend/tui-workbench/src/00-runtime.js#L41)。

### P2：F7 看起来在“搜索”，实际可能只筛当前页

`applyFilter` 仅过滤 `state.currentRows`。服务端分页时，这些是当前已加载页的记录；筛选后仍沿用原来的服务端 pager。于是可能出现“没有匹配记录”，但其他页实际上有目标记录；分页总数也不一定是当前条件的匹配数。

**建议：**主搜索框搜索整个查询范围，条件变化后回到第一页；服务端不支持时，明确写“筛选当前页”或“筛选已加载记录”。不要显示“无匹配数据”来暗示整个数据集没有结果。全量排序也应发生在分页之前。

验收示例：第 1 页没有股票 A、第 3 页有；全量搜索 A 能直接找到。若仅支持当前页筛选，界面清楚说明范围，不承诺全量搜索。

证据：[筛选与分页共存逻辑](../../frontend/tui-workbench/src/40-views.js#L86)。

### P3：分页条缺少定位能力，对未知总量的表达也不准确

通用分页条只有上一页、下一页、页码与总行数，没有每页数量、页码跳转或记录范围。未知 `total_rows` 被默认显示成 0，`total_pages` 缺失时显示横线；对于游标数据，“未知”与“零条”含义不同。

**建议呈现：**

```text
每页 [20 ▾]    第 21–40 条，共 286 条    ‹ 上一页    第 [2] / 15 页    下一页 ›
```

只在后端支持随机跳页、总数可靠时提供页码跳转。游标分页改为“已加载 40 条 · 还有更多”，按能力提供上一批/下一批，不能编造总页数。分页条固定在列表区域可见位置，翻页后焦点回到新页第一行；具体滚动布局需在真实页面验证。

证据：[分页条](../../frontend/tui-workbench/src/40-views.js#L188)、[分页参数与游标处理](../../frontend/tui-workbench/src/40-views.js#L1118)。

### P4：详情返回、刷新和翻页的位置语义没有统一

`renderDataGrid` 每次设置客户端页为 1；切屏同时清空筛选与选中对象。服务端页码可随请求恢复，但跨屏返回没有统一保存完整查询状态。用户在第 5 页查看记录后返回，需要重新翻页和定位。

**建议：**列表状态包含查询条件、排序、页码或游标、页大小、选中对象及滚动位置。刷新当前列表保留状态；主动更改筛选才回第一页。删除当前页最后一条时回到有效页并解释，而不是留空或回首页。

证据：[结果表初始化](../../frontend/tui-workbench/src/40-views.js#L78)、[屏幕重置](../../frontend/tui-workbench/src/10-navigation.js#L295)。

### P5：分页契约需要检查“数字正确但无法真正翻页”的情况

通用服务端投影会生成 pager，并截取 `normalized_rows[:page_size]`；没有明确大小和总数字段时，默认页大小为 20。是否能取到后续记录依赖 owner 查询是否真的接受并使用分页参数。如果 owner 返回完整数组却不支持页码，这种组合可能出现第一页重复或“下一页”无效。

这是**需逐动作验证的风险**，本次没有声称线上某个列表已发生此故障。不能仅凭返回了 pager 或页面显示“共 N 页”判定分页已完成。

建议为每个完整列表声明分页能力、过滤和排序范围、总数是否精确。验证 45 条记录的 20/20/5 分页，三页 ID 不重不漏；游标列表以稳定次序验证批次连续性。小型全量集合可在客户端分页，但不得先把数据截断后再假装可以访问剩余记录。

证据：[服务端集合投影](../../apps/terminal/application/tui_workbench_collection_result_models.py#L243)。

## 4. 推荐的目标交互

一个完整列表只围绕一个任务展开：顶部是名称、范围和更新时间，其下是搜索与筛选；中间表格提供关键列与行操作；底部统一分页。

点击详情后在侧栏或同屏详情区查看，关闭后回到原行。跨工作区处理时，明确携带对象并保留返回位置。翻页时保留表头、条件和当前页内容，仅显示局部更新状态；收到新页再替换表体。错误提示放在表格附近，保留原页让用户继续核对。

Alpha 的“取前 N 名”与“每页 N 条”需要拆开：前者决定研究候选集合，后者只决定浏览方式。选择前 100 名，不应强制一次画出 100 行；也不能把翻页变成重新计算候选排名。

日志或事件流可以另设“加载更多”，交易审核、持仓和候选列表优先使用可定位的分页。不要全站统一改成无限滚动。

## 5. 实施与验收顺序

| 顺序 | 工作 | 完成标准 |
|---|---|---|
| 1 | 真实慢场景测量 | 对今日总览、Alpha 清单、账户列表分别记录首次、二次进入、翻页和详情返回；拆分请求等待、服务端、传输、渲染，不混用测试夹具耗时 |
| 2 | 统一列表与分页交互 | 摘要/完整列表区别明确；每页大小、范围、搜索作用域与未知总数正确；分页不重复、不漏项 |
| 3 | 减少等待感与重复工作 | 翻页不清整屏；返回保留查询及位置；辅助加载不妨碍主任务；失败可就地重试 |
| 4 | 根据瓶颈优化实际速度 | 只针对证据指向的慢查询、数据聚合、传输量、重复请求或渲染量整改，再用同场景对比 |

建议体验目标：点击后 100ms 内有明确反馈；本地已加载数据翻页目标 200ms 内；服务端翻页 P95 目标 1s 内；首个可用主内容 P95 目标 2s 内。**这些是建议验收预算，不是当前实测结果或实现承诺**，应结合生产网络与业务负载确认。即使超时，也应维持稳定布局、可理解的进度和可恢复操作。

测速至少区分冷/热加载、普通/管理员角色和不同数据规模。保留请求数、响应字节、最长任务、首个有效内容时间、翻页时间及用户重定位次数；不要只报告平均接口耗时。
