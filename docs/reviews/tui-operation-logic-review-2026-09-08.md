# TUI 操作逻辑评审与优化建议

> 评审重点已按用户补充意见调整为 UI/UX 的响应速度与分页。请优先阅读[《响应速度与分页专项评审》](tui-speed-pagination-ux-review-2026-09-08.md)；本文保留为操作逻辑补充材料。

评审日期：2026-09-08  
代码基准：`285733cb6`  
评审对象：AgomTradePro `/tui/`，覆盖导航、任务表单、结果视图、面板筛选、行操作、异步任务和每日工作流。

## 1. 核心判断

TUI 已有完整的任务界面基础：每日决策导航、个人与管理员入口区分、主操作折叠预算、同屏治理回执、敏感操作确认、结构化错误恢复。当前最值得投入的方向是**让用户连续完成一件事时，操作含义明确、上下文不丢失、完成状态可信**。

建议优先处理三件事：

1. “刷新”只更新信息，AI 再次执行必须使用独立入口。
2. “已完成”区分查看过、已提交、业务成功和受阻，避免把调用成功当作任务完成。
3. 保留切屏前的筛选、选中对象和非敏感草稿，使用户能够从详情回到原来的工作位置。

本次列出 8 项优化。P1 表示优先影响操作含义或连续任务完成；P2 表示一致性和效率改善。这里的优先级是本报告建议，不修改现有治理单元或生产门禁。

### R1：刷新会重新调用 AI 动作，长任务的刷新指引容易误导

**用户场景：**发送助手请求后按 F5，希望更新结果；或排队任务运行较久，按页面提示“稍后刷新状态”。

`refreshCurrent` 只把 `write/admin` 排除在重跑之外，`risk=ai` 会带着上次参数再次调用 `runAction`。CLI 的普通请求和排队请求均声明为 `ai`。长任务 `consumeQueuedRun` 最多轮询 20 轮，结束后提示“服务器端任务仍在运行，可稍后刷新状态”，与上述刷新分支不一致。20 轮包含网络等待，不能简单等同于 20 秒。

**影响：**普通 AI 请求可能再次消耗调用资源；排队任务可能重复提交创建请求。排队路径保留了 `client_request_id`，后端可能去重，因此本次不认定一定产生重复任务或重复执行。

**建议：**F5 按明确的安全读取契约刷新；已有运行编号时只查询该运行的状态与事件。单独提供“再次执行”，提交前显示任务说明。离开长任务后提供“查看当前运行”，恢复观察而不是重新创建。不得把只读能力简单等同于某个 HTTP 方法。

**验收：**首次提交后连续按 F5，任务提交次数仍为 1；状态读取次数增加；运行超过当前轮询上限、切屏返回及短暂断网后，均能继续观察同一运行编号。

证据：[刷新逻辑](../../frontend/tui-workbench/src/50-shell.js#L333)、[轮询与执行流程](../../frontend/tui-workbench/src/30-actions.js#L818)、[AI 动作风险声明](../../apps/terminal/infrastructure/tui_metadata_runtime_injection_cli.py#L32)。

### R2：主流程进度表示“调用过”，与“业务完成”存在语义距离

**用户场景：**用户看到“主流程 3/3”或“本屏主流程已完成”，自然理解为相关工作已经完成。

`runAction` 在补参数、确认、验密分支之后，直接调用 `markActionCompleted`。该函数只根据主操作和 screen/action key 记进度；调用点没有检查业务 `outcome`，也没有等待排队任务终态。当前 CLI 排队动作本身是 operation，因此不能把“排队立刻计入主流程”当作该具体动作的已发生问题，但通用机制不具备终态语义。

进度保存在按用户隔离的 sessionStorage 中，记录没有数据基准日、账户或输入参数维度。长时间保留同一标签页、换账户参数或换日时，旧勾选没有对应的自动失效规则。

**建议：**短期将调用记录称为“本次已查看/已操作”；需要业务完成度的流程，以后端返回的业务状态为准，区分“已提交、处理中、已完成、部分完成、受阻、失败”。进度应绑定必要的账户、业务日期及上下文版本，避免换对象后沿用旧完成提示。

**验收：**200 响应携带 blocked/partial 时不显示全流程完成；排队未结束不计业务完成；切换账户及业务日期后，相关进度重新核验。

证据：[完成标记调用点](../../frontend/tui-workbench/src/30-actions.js#L972)、[主流程进度与下一项](../../frontend/tui-workbench/src/50-shell.js#L550)、[进度存储](../../frontend/tui-workbench/src/00-runtime.js#L720)。

### R3：同屏操作能保留输入，但跨屏返回会重建工作状态

**用户场景：**在 Alpha 清单选择账户与数量，去看持仓再返回；或在表单填写到一半，临时打开另一个工作区查资料。

同屏任务筛选和展开折叠已经有保留表单 DOM 的测试；问题集中在屏幕重建：`renderScreen` 重置表格筛选和选中对象，再重绘任务表单；`renderDashboardHome` 清空 `dashboardFilters`；浏览器返回重新加载 screen。未看到对应的跨屏草稿恢复路径。

**影响：**用户需要重复选择账户、重新定位行、重填尚未提交的内容。特别是 Alpha 账户范围，返回后恢复默认通用研究可能改变用户正在查看的数据范围；这不是后端越权或决策门禁失效。

**建议：**按用户与工作区保存非敏感工作状态：筛选、排序、页码、选中对象、展开区域和滚动位置。普通表单保留会话内草稿并显示“已恢复草稿”；密码、令牌和文件不持久化。确实无法保留的未提交内容，在离开时提供明确选择。

**验收：**设置账户和数量→查看其他屏→返回，范围不变；填写普通备注后切屏返回，内容仍在；敏感字段没有进入存储；对象删除或权限变化时安全失效并说明原因。

证据：[屏幕状态重置](../../frontend/tui-workbench/src/10-navigation.js#L265)、[面板筛选初始化](../../frontend/tui-workbench/src/20-dashboard.js#L1)、[浏览器返回处理](../../frontend/tui-workbench/src/50-shell.js#L1076)。

### R4：通用“进入处理屏”没有把当前行对象带过去

**用户场景：**打开某条待办或事件的行详情，点击“进入处理屏”，期望继续处理刚选中的对象。

通用行详情读取行内 `target_screen/target_action_key`，先加载目标屏，再用空 `params` 调用目标动作；`loadScreen` 同时清理选中对象。该通路没有显式传递当前行标识。目标动作若需要对象参数，用户会再次补填。现有同屏 `row_actions.param_map` 已支持明确参数映射，可以复用其思路。

**建议：**增加受校验的跨屏任务意图，包含目标屏、目标动作及允许传递的对象标识；沿用现有深链接的安全规则。到达后显示“正在处理：对象名称”，写入、AI 和需确认动作只预填并聚焦，不自动提交。

**验收：**从对象 A 行进入处理后显示 A，不要求重新抄写 ID；缺少或失效对象给出恢复路径；目标动作不可见时明确阻断，不换成其他任务。

证据：[通用行详情跳转](../../frontend/tui-workbench/src/50-shell.js#L198)、[现有下一步动作支持显式参数](../../frontend/tui-workbench/src/40-views.js#L239)。生产中具体哪些行发布此跳转字段，需要运行时样本补齐。

### R5：部分业务行操作只有列表刷新，没有保留结果回执

IA 中政策批准、拒绝、回滚、豁免等动作声明了 `refresh_panel_key`，但没有 `result_panel_key`。前端针对有刷新目标、无结果目标的操作只刷新来源面板，没有把返回业务视图保留在回执区。同样模式还出现在部分策略配置和风控提醒操作。

**影响：**处理后行从待办列表消失时，用户难以就地确认“刚处理了谁、结果是什么、理由是什么”。通用状态文案也可能只说明工作区刷新完成。

**建议：**把已有治理回执模式推广到这些配置：操作对象、业务结果、时间、理由、后续动作保留在同屏回执；只刷新受影响列表。partial/blocked 必须显示真实结果。新增面板前核对运行时覆盖，避免重复创建已有回执。

**验收：**批准后列表更新，回执仍显示对象与结果；拒绝/回滚保留理由；部分失败不能只显示“已更新”。

证据：[政策行操作配置](../../config/tui/ia/tui_information_architecture.v1.json#L54)、[目标面板处理分支](../../frontend/tui-workbench/src/30-actions.js#L974)。当前已通过的同屏治理回执测试证明实现基础存在，不代表所有业务屏配置一致。

### R6：固定八步顺序和页面“下一步”提示不完全一致

环境与脉搏页提示下一步进入 Beta/Alpha 清单，但 IA workflow 中该屏之后是政策与热点。用户按 F4 与按说明继续，会走不同路径。此外，固定顺序先进入每日决策流，再进入候选、账户和风控检查，容易让新用户混淆“初步建议”和“已核验结论”。后者属于设计判断，不是金融规则错误。

**建议：**保留八步导航作为浏览路径，同时明确“推荐下一任务”和“继续浏览下一屏”的区别。日常任务可呈现“确认数据及环境→研究候选→核对账户与风控→形成或修订结论→复盘”的上下文依赖；实际业务规则仍由所属应用判定。已具备有效上下文的用户允许跳到需要处理的任务。

**验收：**按钮、说明、快捷键指向一致或清楚注明差异；缺少前置数据时显示可执行的补齐入口；不能用“走完八屏”替代决策授权。

证据：IA 中 `macro-regime.overview.user_experience.next_step_hint` 与文末 `workflow`；[IA 注册表](../../config/tui/ia/tui_information_architecture.v1.json)。

### R7：快捷键提示过于简略，容易把执行理解为导航

底栏写“F6 下一项”，实际是执行本屏下一主流程任务；底栏写“Esc 返回”，实际主要关闭菜单、筛选、抽屉或弹窗，没有一般意义上的上屏返回。帮助弹窗中的解释更准确，但需要用户先打开才能理解。

**建议：**改成“F6 执行下一任务”“Esc 关闭浮层”，并提供明确可点击的“返回列表/返回上一工作区”。关键动作不要只放在快捷键帮助中；快捷键与按钮使用相同名称和确认规则。

**验收：**新用户仅看底栏即可预测动作；Esc 在无浮层时不暗示能够返回；鼠标与键盘均可走完整条任务链。

证据：[工作台底栏](../../core/templates/terminal/tui_workbench.html#L139)、[快捷键帮助与执行函数](../../frontend/tui-workbench/src/50-shell.js#L235)。

### R8：就绪和刷新时间的口径需要更清楚

模板顶部固定显示“工作台：已就绪”。dashboard 渲染发起异步面板读取后，`renderScreen` 就更新“上次刷新”并报告概览加载状态，未等待所有业务面板成功。面板自身已有错误隔离和恢复能力，因此问题是全局提示的含义，不应据此认定业务 freshness 判定错误。

**建议：**全局区分“界面就绪”“部分数据加载中”“部分数据不可用”；时间明确标为“本次请求时间”或“最近成功更新”。数据观测时间、可靠性与禁止用于决策状态仍由各业务面板提供，不用页面刷新时间替代。

**验收：**一个面板成功、一个失败时，全局显示部分可用；失败面板不能借全局刷新时间显得刚更新成功；业务源时间始终保留。

证据：[顶部静态状态](../../core/templates/terminal/tui_workbench.html#L35)、[面板加载与屏幕完成提示](../../frontend/tui-workbench/src/10-navigation.js#L328)、[P0 与延后面板加载](../../frontend/tui-workbench/src/20-dashboard.js#L71)。

## 4. 建议保留的已有设计

- 个人自助与系统治理已分流，不需要重新拆一遍导航。
- 参数完整的安全读取深链接可自动执行；写入、AI、确认类任务按显式交互处理。
- 同屏治理列表、回执与局部刷新已有实现和测试，应推广现有模式。
- 主任务预算、更多任务折叠、同屏输入保留已存在，不能仅用 action 总数认定界面超载。
- 密码遮罩、模态焦点约束、结构化错误恢复、过期响应隔离、图表文本摘要和多视口几何测试已有覆盖。
- 屏幕地址输入是当前规范明确要求的导航能力，保留即可，不应按旧整改记录将其当作需要删除的技术词泄露。

## 5. 建议实施顺序

| 批次 | 范围 | 可交付结果 |
|---|---|---|
| 第一批 | R1、R2 | 刷新不触发 AI 重执行；调用进度和业务完成状态明确区分 |
| 第二批 | R3、R4 | 选股→账户→返回可恢复范围；从行进入处理自动带入正确对象 |
| 第三批 | R5、R6、R7、R8 | 回执、下一步导航、快捷键及全局状态统一 |

任务上下文和导航契约应由 metadata 声明，并同步 schema、校验器、运行时与测试；业务完成判定属于 owner application，不能搬入通用前端或 terminal。本文是评审报告，不设立新的平行治理真源；采纳后应并入现有 TUI 计划和注册表。

## 6. 下一轮真实界面验收清单

1. 普通用户：选定账户、设置 Alpha 数量，查看标的/持仓后返回，确认对象、范围和位置没有变化。
2. 普通用户：填写非敏感备注，切屏返回及取消提交，确认内容保留且未产生写入。
3. AI 使用者：任务运行超过当前轮询上限，多次刷新、离开返回、网络中断后恢复，确认只有一次创建请求且始终观察同一运行。
4. 管理员：选择测试对象执行批准、拒绝及带理由的回滚，确认来源列表和回执一致；该项需要受控测试数据及相应业务写入授权。
5. 业务状态：以 success/partial/blocked/failed 及过期数据样本验证主流程进度和状态提示。
6. 键盘使用者：仅用键盘完成筛选、查看、返回、编辑、确认及取消；再核对鼠标入口名称一致。

建议采集完成率、重复输入次数、返回后重定位次数、误触发提交次数，以及受阻后能否找到下一步。当前没有用户样本和耗时基线，不给出未经测量的效率提升百分比。
