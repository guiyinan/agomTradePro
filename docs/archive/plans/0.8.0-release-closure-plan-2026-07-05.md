## 1. 背景

当前系统的核心业务能力已经基本齐备，但仍处于“功能已完成、工程收口未完成”的状态：

- 公开版本号仍停留在 `0.7.0`，2026-03-23 之后的大量能力仍以开发快照存在。
- `task_monitor / readiness / scheduler / VPS` 在最近三天持续高频变更，说明运行与验收链路仍在补尾。
- 当时的文档叙事索引、版本说明和系统现状之间存在时间差，尚未完全追平当前代码。
- TUI 与治理层已经成为主入口，但仍存在中心大文件和历史桥接债务，需要继续拆分。

因此，下一阶段不应继续横向扩功能，而应集中完成一次 `0.8.0` 收口发布。

---

## 2. 计划目标

本轮计划只解决 3 类问题：

1. **发布收口**：把当前开发快照整理为可发布的 `0.8.0`。
2. **生产稳定化**：把定时任务、readiness、VPS 运行和数据持久化做成可重复验证的闭环。
3. **架构减债**：继续压缩 TUI 大文件和 `core/integration` 历史桥接债务，避免后续继续堆积。

本轮计划**不新增大业务模块**，只允许补齐现有主链路、治理与运维闭环。

## 4. 分阶段执行

### Phase A: 发布基线收口

目标：把“当前到底是什么版本、包含哪些能力、如何描述系统状态”统一下来。

工作项：

- 更新 `0.8.0` 版本号与 build 日期
- 整理 `0.7.0` 之后开发快照，形成正式发布说明
- 同步 `AGENTS.md`、`docs/VERSION.md`、`docs/INDEX.md`、`docs/governance/SYSTEM_BASELINE.md`
- 明确当前“生产就绪”与“正式发布”的区别，避免状态表达冲突

退出条件：

- 文档口径一致
- 发布说明可独立阅读
- 新开发者只看文档即可知道当前推荐入口、推荐部署方式和当前版本边界

### Phase B: 运行与验收闭环

目标：把 `task_monitor + readiness + scheduler + VPS` 做成稳定可复用能力。

工作项：

- 统一 readiness monitor 的证据口径
- 固化 `worker / beat / periodic task / evidence` 的标准检查链
- 清理“只适合人工排障、不适合作为正式验收”的脚本路径
- 把 VPS bundle 部署后的检查项写成固定 runbook

退出条件：

- 本地可重复完成 strict acceptance
- VPS 可重复完成 scheduler-clean 验收
- 失败时能从页面或命令直接定位到具体断点

### Phase C: 生产底座定型

目标：把部署与数据持久化从“可以跑”提升为“明确推荐怎样跑”。

工作项：

- 明确生产数据库标准方案
- 明确 Redis、Celery、日志、evidence、snapshot 的持久化策略
- 明确 bundle / Docker / 三机架构的推荐顺序
- 为正式发布版写清最小上线门槛

退出条件：

- 不再出现互相冲突的生产部署口径
- 新环境部署时不需要再靠历史 commit 反推正确姿势

### Phase D: 架构减债

目标：降低 TUI 和桥接层继续膨胀的风险。

工作项：

- 拆 `apps/terminal/infrastructure/tui_metadata_repository.py`
- 继续把跨模块协作回收到 application facade / provider / registry 边界
- 收紧治理基线，避免“先堆功能再治理”
- 为大文件拆分补齐单元测试和契约测试

退出条件：

- TUI 中心文件不再单点膨胀
- `core/integration` 债务继续下降而不是横盘
- 治理门禁从“防变差”开始进入“持续逼近更好结构”

## 5. 建议优先级排序

建议按下面顺序做，不建议并行开太多线：

1. `P0-1` 发布口径统一
2. `P0-2` 定时任务监控收尾
3. `P0-3` readiness 验收流程固化
4. `P0-4` VPS 连续运行验证
5. `P1-5` 生产数据库策略定稿
6. `P1-6` / `P1-7` 文档与系统基线同步
7. `P1-8` TUI 大文件拆分
8. `P1-9` `core/integration` 债务压缩
9. `P2-10` 发布前统一回归

理由：

- 前 4 项决定系统能不能被称为“可发布、可运行、可验收”。
- 中间 4 项决定发布后是不是“可维护、可交接、可继续开发”。
- 最后一项负责形成最终发布证据，而不是边修边猜。

- 发布前统一回归通过并生成报告

## 7. 风险与约束

### 风险

- 最近 `task_monitor` 和 TUI 都在高频改动，继续混合推进容易互相影响。
- 文档口径分散，如果不先统一版本与基线，后续很难判断“到底哪些已完成”。
- 若不尽快明确生产数据库策略，部署文档会继续分裂。

### 约束

- 不新增大模块
- 不做破坏性 API 契约变更
- 继续遵守四层架构和治理门禁
- 修复必须带测试或验收证据

---

## 8. 完成定义

当以下条件同时满足时，本计划可标记完成：

- `0.8.0` 版本号、文档、发布说明已统一
- `task_monitor / readiness / VPS` 有稳定验收闭环
- 生产部署口径唯一且明确
- TUI 与 `core/integration` 关键技术债完成一轮实质性下降
- 发布前统一回归报告可追溯
