The repository change closes the reported stale blocked-receipt defect for rows that still exist in the owner’s portfolio. `_mark_blocked` has a typed signature, one call site, and returns the locked `TransactionModel` instances it actually updates. It locks the owned portfolio first, then only requested transactions still scoped to that portfolio and owner, in the established trade/code/key/PK order. It leaves `PROJECTED` and `ALREADY_IN_BASELINE` terminal states unchanged, applies the existing blocker/declaration fields to nonterminal rows, and the handler builds results from those refreshed instances. A missing row is omitted rather than reconstructed. The candidate adds no repository dependency or non-ORM I/O.

The lock order agrees with the repository’s fact-write and reconciliation paths (portfolio before batch/fact/position work); I found no new reverse lock edge. The projection-abort transaction is exited before the handler opens `_mark_blocked`’s atomic scope, so a failed projection is rolled back before the blocker receipt is persisted. CAS conflict codes and the original request, declaration time, source hash, actor, and batch continue through unchanged. `attempted_at` is sampled separately after blocker locks are acquired, while `declared_at` remains the earlier decision time. No terminal-state or ordering regression was apparent from static inspection.

One bounded P2 remains outside this repository-only patch: a concurrent deletion can leave the Application response describing a row from its stale initial write record. `reconcile_fact_set` returns only rows still present in the owner/portfolio scope, but `BrokerFactSetReconciliationResult` and its Protocol docstring do not define missing-ID behavior. In `apps/account/application/manual_trade_sync.py`, `_annotate_fact_outcomes` falls back to the original `BrokerFactRecord` when an ID has no reconciliation result. `_fact_state_counts` also uses `repo.get_fact_by_stable_key(...) or initial`, so a deleted row is counted as `AWAITING_BASELINE`/pending. The response can therefore report `pending_fact_count=1` and a pending row even though the row has been deleted. If the portfolio disappears before blocker persistence, the repository raises its typed ownership error; the Application catches it and follows the same initial-state fallback path.

Minimal follow-up: define missing-row semantics at the Application boundary by comparing requested IDs from `writes` with IDs in `reconciliation.facts`. For missing IDs, emit an explicit stable disappearance error/status and do not fall back to the initial state or count them as pending/projected/blocked. Keep `facts_saved_count` as an operation count only if its public meaning is documented as “write succeeded earlier in this request”; do not imply that the row still exists. The repository should continue omitting missing rows; do not recreate a `TransactionModel` or economic fact to satisfy a one-result-per-requested-ID assumption. This is a separate Application/API contract correction and does not invalidate the repository candidate’s intended fix.
